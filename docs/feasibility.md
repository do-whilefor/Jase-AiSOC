# 项目可行性分析

状态：P0 基线草案
评估日期：2026-08-03
依据：项目计划书 V3.3 与当前仓库/本地工具链盘点

## 结论

**有条件可行（Go with gates）**。P0-P7 的 MVP 闭环可以按文档架构实现，完整 V1.0 也具备成熟技术组件支撑；主要风险不在单项技术是否存在，而在跨 Linux 内核兼容、事件语义一致性、证据完整性、容量成本和高风险响应的系统集成。项目必须按 P0-P12 的依赖和退出门禁推进，不能以接口已写完或服务已启动代替攻击回放、故障恢复与边界验证。

## 分域判断

| 能力域 | 判断 | 依据与约束 |
|---|---|---|
| Python 中心平台 | 可行，风险低到中 | FastAPI、Pydantic、SQLAlchemy、gRPC 与 NATS 均有成熟生态；需要严格异步边界和背压。 |
| Linux Agent | 可行，风险高 | Python 适合生命周期和采集编排；eBPF 探针仍需受限 C/libbpf/BCC。发行版、内核、BTF、LSM 和权限组合必须实机验证。 |
| 确定性检测与 Incident | 可行，风险中 | 规则、窗口、序列和实体关联可实现；难点是统一 Schema、乱序/重复、误报数据集和可重放性。 |
| AI 研判 | 可行，风险中到高 | 只能位于 Incident 后的可选 Review Gate；Claim-Evidence 程序校验、预算和 Provider 降级是可行性的前提。 |
| 恶意文件 | 静态分析可行；动态沙箱有条件可行 | YARA-X/ClamAV/ELF 元数据成熟；动态执行必须是独立信任域，不能放在 Agent 或中心服务进程内。 |
| 溯源图谱 | 可行，风险中 | 初期 PostgreSQL entity/edge 与递归查询足够；图数据库应由查询压测触发。技术归因可做，真实攻击者身份归因不在范围。 |
| 自动响应 | 可行，风险高 | 固定动作、目标重验证、审批、TTL、预算、回滚和执行后验证缺一不可；R3 默认人工审批。 |
| 数据平台/HA | 可行，成本高 | PostgreSQL、NATS、对象存储可覆盖 MVP；ClickHouse、OpenSearch 与 HA 只有在容量/SLO 证据支持时启用。 |

## 关键技术取舍

1. **Python 不是内核数据面。** eBPF 使用签名后的 CO-RE 对象/辅助程序或受限 BCC 探针；CPU 密集型哈希、压缩、规则和文件分析进入进程池或独立 Worker。
2. **MVP 不把 AI 作为主链路依赖。** 所有 Provider 不可用时，采集、确定性检测、Incident、证据查询和人工响应继续运行。
3. **组件按测量启用。** 开发基线使用 Base All-in-One；MVP 集成使用 Stream（PostgreSQL + NATS + 对象存储）；ClickHouse/OpenSearch/图数据库不是前置依赖。
4. **事件和证据契约先冻结。** `tenant`、`host`、源时间/接收时间、`boot_id`、`sequence`、`raw_ref` 和完整性字段必须在采集前形成契约测试。
5. **响应面与 AI 面隔离。** 模型只生成建议/结构化 Claim，不得扩大动作权限；Action Runner 不接收任意命令文本。

| 项目 | 当前状态 | 影响/动作 |
|---|---|---|

| Python | 本机为 3.14.6 | 项目目标为 3.12/3.13 主验证；CI 必须覆盖受支持版本，3.14 仅作前向观察。 |

## 资源与组织可行性

完整 V1.0 横跨 Linux 内核观测、Python 分布式后端、检测研究、恶意软件、LLM 安全、前端、SRE 和安全测试。即使阶段不绑定固定人数，也至少需要这些专业能力被明确覆盖；由单一开发流同时承担全部域会使兼容性和安全门禁成为主要进度风险。适合按“契约/平台、Agent、检测/数据集、AI/验证、发布/安全”并行，但共享 Schema 和集成门禁必须单点治理。

## Go / No-Go 条件

继续进入 P1 的条件：P0 的架构、Schema、信任边界、部署剖面和 CI/SBOM 经评审，无阻塞性架构问题。以下任一情况存在时不得进入生产试点：

- 真实攻击回放不能稳定复现或攻击尝试与成功状态混淆；
- 严重结论无法回到原始证据，或存在跨租户/不存在的 `evidence_id`；
- 正常日志绕过 Review Gate 大量触发模型；
- 恶意样本能在 Agent/中心信任域直接执行；
- 高风险响应可绕过审批、目标重验证、预算或回滚。
