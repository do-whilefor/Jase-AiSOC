# Jase-AiSOC V4.0 Rust First 推进记录（2026-08-12）

本记录严格以 `AI-SOC_Rust_AI-Web-Guard_项目计划书_V4.0_RustFirst_实施完善版.docx` 为基线，记录本轮 Linux 沙箱审计、实际修复、可执行验证结果和仍未关闭的 P0–P14 差距。未通过真实编译/运行验证的项目不得标记为完成。

## 1. 本轮 Linux 沙箱事实

- 运行环境：Debian GNU/Linux 13 (trixie), x86_64 Linux。
- 沙箱当前没有 `rustc`/`cargo`、Docker、PostgreSQL 客户端/服务端。
- 沙箱 DNS/外网下载不可用，无法从 Rust 官方分发或 Debian 仓库补装 Rust 1.82 工具链。
- 因此本轮不能真实执行 `cargo fmt/check/clippy/test/build`、SQLx 对 PostgreSQL 的实际 migration、Rust 服务启动以及 API/Agent/Ingest/Web Guard 二进制联调。该限制属于 P1 未关闭阻断，不能用静态检查替代并宣称完成。

## 2. 本轮已完成整改

### P1 / Linux 工程治理

1. 修复 Rust-first 静态门禁在 Linux 中依赖 Python 脚本 executable bit 的问题，改为显式 `python3` 调用。
2. 修复 Makefile 与 GitHub Actions 直接执行 Git 索引中为 `100644` 的 shell 脚本导致 `Permission denied` 的问题，统一使用 `bash script.sh`。
3. 修复 Linux release manager、安装器、部署测试和文档中同类直接执行问题。
4. 实际执行 `make deploy-check` 通过：
   - Rust-first production gate：PASS
   - SQLx/PostgreSQL migration structure gate：PASS（10 migrations / 22 tables）
   - Central PostgreSQL repository structure gate：PASS
   - shell syntax：PASS
   - release manager checksum / tamper reject / signature / rollback：PASS
5. 发现现有 `Cargo.lock` 仍是旧迁移基线：仅 39 个 package，缺少绝大多数默认生产 Workspace crate，也缺少 `serde/tokio/sqlx` 等根级 pinned workspace dependency。`scripts/check-cargo-lock.sh` 正确返回 FAIL。必须在可联网、可信 Rust 1.82 builder 中执行 `cargo generate-lockfile` 后再运行 `cargo metadata --locked` 和完整 Rust CI；禁止手工伪造 lock。

### P3 / Ingest、raw evidence、DLQ、gap/replay

1. 延续已有 Rust PostgreSQL central repository、不可变本地 raw evidence object store、normalize DLQ/lease/replay 路径。
2. 新增 migration `202608120007_event_watermark_reconciliation.sql`，为 `event_watermarks` 增加明确的 `next_expected_sequence`，消除 `highest_contiguous_sequence=0` 同时表示“尚未收到任何事件”和“已收到 sequence 0”的歧义。
3. 修复首个收到的 batch 本身存在前置缺口时错误推进连续水位的问题。
4. 进一步修复 batch 范围误判问题：`EventBatch` 只要求 sequence 严格递增，并不保证 range 内连续，因此 watermark 不再依赖 `ingest_batches.sequence_start..sequence_end`，而是只依据 `raw_event_index` 中实际持久化的逐条 sequence 前进。
5. PostgreSQL 集成测试已补充以下语义（代码已写入，但受沙箱缺少 Rust/PostgreSQL 限制，尚未真实执行）：
   - 初始 sequence 0 -> `next_expected=1`；
   - 先收到 2、后收到 1 -> 水位先停在 1，再收敛至 3；
   - 同一 sparse batch 中只存在 3、5 -> 水位停在缺失 4；
   - 后补 4 -> 自动跨过已保存的 5，收敛至 6。
6. `check-central-repository.py` 已同步检查 gap-safe watermark 必须以 `raw_event_index` 的实际 sequence 为事实依据。

### P4 / Detection 主体隔离

1. 对照旧 Python 规则行为确认：Web Recon/SSH burst 的窗口键必须包含攻击主体；同一 host 上不同来源不能共享同一个 burst。
2. Rust Web Recon 现按 `src_ip` 独立分组后再计算 request/unique-path/4xx/sensitive-path 指标，缺少 source IP 的事件不进入来源型 burst。
3. SSH brute-force 使用 `src_ip:{source}` 作为 entity key，缺少 source IP 的事件不参与同源暴破计数。
4. Web injection 的单事件 entity key 同时保留来源与 event anchor，便于 P6 将同一攻击主体的后续证据有界关联。
5. 新增 Rust 单测覆盖“两个来源不可合并”和“同一来源可形成 Web scan”；代码已写入，但本沙箱无 Rust 工具链，尚未真实 `cargo test`。

### P6 / Incident revision、证据边界与幂等

1. 重写 Rust `IncidentCorrelator`：只允许同 tenant、同 host、共享主体/证据 anchor 且时间间隔不超过默认 900 秒的 Detection 聚合；同 host 不同 source、同 source 超窗均创建新 Incident。
2. Detection 时间先按 RFC3339 解析再排序，拒绝非法/反向时间窗；同一 Detection 被绑定到两个 Incident、迟到 Detection 同时桥接多个既有 Incident、容量/修订溢出等情况 fail closed，并保证失败时不修改 correlator 状态。
3. 修正安全状态强度顺序为 `observed < blocked < attack_attempt < suspected_success < confirmed_compromise`，避免 blocked 反向压过后续攻击尝试/成功证据。
4. 新增 SQLx migration `202608120008_incident_revision_history.sql`：`incidents` 仅作为最新 materialized state；所有 Incident revision 追加保存并绑定 snapshot SHA-256，同 revision 不同内容返回 `DataConflict`。
5. 新增 `GET /api/v1/incidents/{incident_id}/revisions`，读取始终使用认证 principal 的 tenant，不接受客户端指定 tenant。
6. 新增 migration `202608120009_incident_revision_context.sql`：每个 revision 独立保存 Detection membership、evidence event refs 与 entity keys；evidence event 使用 `(tenant_id, event_id)` 复合 FK 指向 `normalized_events`，跨租户引用由数据库边界拒绝。
7. 修复 central repository 幂等语义：Normalized Event/Detection 的同 ID 重试只在完整内容相等时幂等；同 key 不同 canonical 内容返回 `DataConflict`，不再覆盖旧事实。
8. PostgreSQL integration test 已增加 revision append/idempotency/conflict、revision evidence/entity relation 检查；受当前沙箱无 PostgreSQL/Rust 限制，尚未真实执行。
9. 旧 Python `tests/unit/test_incident_correlator.py` 作为迁移行为基线在本沙箱实际执行：6 passed；它不是 V4 production runtime。

## 5. P6 Evidence custody / retention 本轮继续增量

1. 新增 SQLx `202608120010_evidence_custody_retention.sql`，把 raw event 对应的 authoritative `evi_*`、hash/size/source、integrity、retention、encryption key reference、custody chain、legal-hold/lifecycle event 和 Incident revision evidence 绑定纳入 PostgreSQL 权威模型。

3. legal hold 只追加 `apply/release` 事件，不覆盖 evidence row；跨租户、重复状态、矛盾 event ID、时间倒退 transition 均 fail closed。
4. Rust API 新增 `GET /api/v1/incidents/{incident_id}/evidence`，tenant 只能来自认证 principal；响应返回当前 revision 的 evidence/custody/retention/legal-hold/lifecycle 投影。
