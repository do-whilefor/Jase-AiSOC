# AI-SOC 重构记录（2026-08-11）

## 依据与结论

本轮以 `AI安全分析与溯源_项目计划书_Python.docx` 为产品方向，以仓库实际调用链和测试为实现依据。计划书的核心边界保持不变：Linux Agent/传感器先采集并标准化，确定性检测形成 Incident 与证据包，AI 在 Incident 粒度执行分析和审核，响应必须经过策略、审批和目标重验证。

计划书原先以 Python 为主要实现语言。本轮按照新的工程目标调整为 **Rust Core + Python AI/Service Layer**，但没有重做成不同产品，也没有把全部 Python 机械翻译成 Rust。

## 已完成的结构重构

- 新建根 Cargo Workspace：`Cargo.toml`。
- 新建 `crates/aisoc-core` 与 `crates/aisoc-python`，删除旧的单一薄 Rust crate。
- Python 包从 `src/blue_team` 统一迁移为 `src/aisoc`；CLI、migrations、tests、scripts、coverage 与 import 同步迁移。
- 部署入口从发行版特定目录迁移为 `deploy/linux`。
- systemd unit 统一为 `aisoc-api`、`aisoc-ingest`、`aisoc-agent`。
- 环境变量统一为 `AISOC_*`，schema host 统一为 `schemas.aisoc.local`。
- 删除项目运行路径中的 Windows 分支和 Windows 专属锁/信号/进程处理。
- 删除历史 Rust 目录和 `state/blackboard.md` 等无运行价值的过程文件。

## Rust 化范围

### 已迁移

`aisoc-core` 当前包含：

1. Hashing
   - SHA-256。
   - HMAC-SHA256。
   - 常量时间比较。
   - 有界流式文件 SHA-256；Linux 打开选项包含 `O_CLOEXEC`、`O_NOFOLLOW`、`O_NONBLOCK`，并检查普通文件、大小上限、扫描期间增长以及 mtime/ctime/size 变化。

2. Linux capability probe
   - `/etc/os-release` 解析。
   - distro、init、cgroup v1/v2、BTF、LSM、journald、auditd、eBPF 与包管理器能力报告。
   - 能力缺失走 degraded/unavailable，不以单个工具缺失结束整个 Agent。

3. Static analysis
   - Shannon entropy。
   - 有界 printable strings。
   - ELF magic/class/endian/machine 基础解析。

4. IOC matcher
   - IP、domain、SHA-256 标准化后的精确匹配。
   - PyO3 暴露只读 matcher 给 Python enrichment。

### 暂留 Python

以下内容暂不迁移：

- LLM SDK、Provider、Prompt、EvidencePackage、Verifier/Adjudicator。
- FastAPI 路由与服务生命周期。
- SQLAlchemy repository 与 Alembic migrations。
- 仍在快速迭代且没有明确性能瓶颈的业务编排。

理由是这些模块迁移 Rust 的工程收益目前低于接口重写、生态替换和验证成本。后续 Rust 迁移优先级应继续放在 Agent collector、procfs/netlink、日志解析、规则匹配和高吞吐预处理，而不是追求语言占比。

## Linux 通用化

运行路径不再维护 Windows 行为。Agent supervisor、installer、process lock、collector、identity/release 和 response 路径统一采用 Linux/POSIX 语义。

通用安装器：

- 检测 apt/dnf/yum/zypper/pacman，但默认不主动安装系统包。
- 不假设 systemd；通过 `/proc/1/comm` 检测，缺失时给出手动 supervisor 命令。
- 不假设本地 PostgreSQL。
- 不生成假的 Agent 身份、证书或 enrollment 结果。
- 常规安装默认要求预构建 Rust wheel 或 Cargo 1.82+；只有显式开发参数才允许 Python core fallback。
- Agent 配置以 `aisoc:aisoc`、`0600` 安装，与运行时私有配置检查保持一致。
- 采用 `aisoc` 服务账号与 `/opt/aisoc`、`/etc/aisoc`、`/var/lib/aisoc*` 路径。

仍保留对 `C:\...`、反斜杠、`..` 等异常归档路径的拒绝语义。这不是 Windows 兼容代码，而是 Linux 服务处理不可信归档时的路径穿越防护。

PE 静态分析同样保留：Linux SOC 可能接收到 PE 样本，解析文件格式不等于支持 Windows 运行平台。

## 新增确定性 IOC 链路

新增 `src/aisoc/enrich/ioc.py` 与 `ioc.exact_match` 规则：

- Feed 必须是普通、非 symlink、单 hardlink、非 group/world-writable 文件。
- 在 JSON/Pydantic 解析之前校验固定 SHA-256。
- 最大 8 MiB / 100,000 indicators。
- indicator 支持 IP、domain、SHA-256，过期项启动时排除。
- Suricata HTTP hostname 与 DNS query 被标准化到 `network.domain`，进入域名 IOC enrichment。
- 命中结果只产生 `suspected_success/high` 确定性检测；不会绕过证据关联直接宣称 confirmed compromise。
- 规则继续受既有签名 lifecycle/catalog 控制。

该实现是本地固定数据源，不冒充完整的 P11 managed threat-intel 生命周期。

## 安全清理

本轮重点检查并收紧：

- shell/子进程：Agent supervisor 不继承 `PYTHONPATH` 等开发环境变量；进程组与 signal 使用 Linux 语义。
- 文件：敏感 feed/hash/installer 路径拒绝 symlink，并对 mode/type/size 做检查。
- archive：保留路径穿越、绝对路径、反斜杠和 drive-like 输入拒绝。
- secret：安装器不生成或提交 token/CA/private key；本地 `.env` 不纳入交付包。
- runtime packaging：CI release job 生成独立 PyO3 wheel，Docker 构建必须安装并成功 import `aisoc_rust`，不再静默发布 Python-only 镜像。
- AI：LLM 仍只处理有界 EvidencePackage，不逐条审查原始日志。

## 实际验证

本轮已在当前沙箱执行：

- Python `compileall`：`src`、`tests`、`scripts`、`migrations` 通过。
- 重构主回归集：189 passed，覆盖 config、Rust bridge fallback、Linux capability、恶意文件静态分析、IOC、Normalize/Detection、Agent supervisor/installer/process/identity/release/artifact 等路径。
- Schema 由模型重新导出后执行 `python -m aisoc.domain.schema_export --check`：通过。
- `bash -n deploy/linux/install.sh`：通过。
- `uv lock --check --offline --python /usr/bin/python3.13`：通过。
- 完整 `tests/unit` 当前在 collection 阶段得到 10 errors / 1 skipped，根因是沙箱缺少锁定依赖 `structlog`，`yara_x` 也未安装；`uv sync --offline` 又缺少本地缓存的 `pydantic-settings` / `cyclonedx-python-lib`，且当前环境无外网，不能补齐依赖。
- `ruff`、`mypy` 和前端 `node_modules` 同样不在当前沙箱，因此对应 lint/typecheck/console test 未伪装为已执行。
- 当前沙箱没有 `rustc`/`cargo`，且 DNS/网络不可用，因此无法在本地真实执行 Cargo 编译。CI 已配置真实 `cargo fmt --check --all`、`cargo check --workspace`、`cargo clippy --workspace --all-targets --all-features -D warnings`、`cargo test --workspace` 与 PyO3 构建门禁；在具备 Rust toolchain 的环境中必须让这些门禁实际通过后才能把 Rust 编译标记为已验证。

没有因为环境缺少 toolchain 或依赖而用假构建、假测试结果替代验证。
